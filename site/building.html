From a bare Windows machine to a running app

Building from source.

No release exists yet, so building from source is currently the only way to run yt-dlp Studio. The two scripts below install every dependency themselves — starting from a machine with nothing on it — using the exact same packaging path the (not-yet-published) CI release would use.

1. Clone the repository, with submodules

yt-dlp and ffmpeg are both pinned Git submodules, so they need to be fetched along with the main checkout.

git clone --recurse-submodules https://github.com/Ding-Ding-Projects/material-ytdlp.git

2. Run download-dependencies.bat

Fetches every build-time dependency the project needs — pinned versions, verified digests, into a user-scoped location, never machine-wide.

download-dependencies.bat

Add /s for a silent, unattended run with no prompts — the mode CI and scripted machines use.

3. Run build.bat

Builds the renderer, the compiled yt-dlp.exe from the pinned submodule, and the compiled ffmpeg binaries, then offers to launch the app. This script has not yet completed end to end in this project's own history, because the renderer build is still in progress — see the roadmap.

build.bat

4. Optional: build-installer.bat

Produces the same unsigned Squirrel.Windows installer a real release would carry, and verifies its own output — file exists, expected size and shape, SHA-256 reported. This script has also never yet produced an installer end to end.

build-installer.bat /s

Compiled, not downloaded

Both bundled binaries come from source the project pins itself, not from a prebuilt release fetched off the internet.

yt-dlp

Compiled from the pinned vendor/yt-dlp git submodule using PyInstaller, at build time. The submodule tracks yt-dlp's master branch and is advanced on every pull, because yt-dlp regularly needs upstream fixes when a site changes its player.

ffmpeg

Compiled from the pinned vendor/ffmpeg git submodule, from the FFmpeg source tree directly — not a third-party static-build mirror. Same tracking policy as yt-dlp.

The LGPL decision

Why --enable-gpl and --enable-nonfree are never passed.

The ffmpeg build is compiled as an LGPL build. --enable-gpl is never passed at configure time, and --enable-nonfree never will be. That is a deliberate licensing choice, not an oversight — it keeps the compiled binary redistributable inside an unsigned installer without carrying GPL or non-free obligations the project has not taken on.

The practical consequence: libx264 (the GPL-licensed H.264 encoder) is not compiled in. Muxing, remuxing, format conversion and audio extraction — the overwhelming majority of what yt-dlp Studio uses ffmpeg for — are unaffected. What is lost is ffmpeg's own libx264-backed re-encode path; anything relying on that specific encoder is out of scope for this build.

How long a cold build takes

Roughly, on a machine with nothing pre-installed.

  • Dependency fetch: the bulk of the wall-clock time on a cold machine, since it is fetching a compiler toolchain, an SDK and every project dependency it does not find already installed.
  • ffmpeg compile: the single longest individual step — compiling a full C codebase from source is not fast on any machine.
  • yt-dlp PyInstaller build and the renderer build: comparatively quick once their own toolchains are in place.

An exact minute figure isn't published here, because neither build.bat nor build-installer.bat has completed end to end yet in this project's own history — see the honest status in HANDOFF.md. Both scripts re-run warm rather than cold once their caches exist, which is faster.
